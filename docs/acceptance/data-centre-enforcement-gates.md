# Impilo vNext Data Centre Enforcement Gates

## Purpose

This acceptance pack defines the Impilo-specific gates that must pass before a data centre sandbox deployment is accepted or promoted. It extends generic Kubernetes readiness with Health OS governance requirements.

These gates apply to Kubernetes/OpenShift sandbox environments. Local Docker Compose can be useful for development, but it is not sufficient evidence for data-centre acceptance.

## Gate Summary

| Gate | Requirement | Minimum evidence |
|---|---|---|
| G1 | Envoy -> TSHEPO/OPA -> service enforcement | Unauthorized protected request denied at gateway; authorized request allowed and logged |
| G2 | Mandatory trust headers | Requests missing required trust headers are rejected or enriched only by an approved trusted component |
| G3 | No direct public service exposure | Only approved ingress/gateway services have public routes/load balancers |
| G4 | No UI-to-database/cache/bus access | UI namespaces cannot reach PostgreSQL, Redis, Kafka, or object storage directly |
| G5 | Per-service DB credentials | Each service uses its own DB user with least privilege |
| G6 | Audit and outbox behaviour | Protected workflows write audit records and reliable outbox events |
| G7 | Synthetic-only PII | Sandbox contains only generated/test PII; no real patient/provider data |
| G8 | FHIR/BUTANO PII separation | BUTANO/FHIR records use CPID/approved identifiers only; PII remains in VITO/identity stores |
| G9 | Namespace security boundaries | Deny-by-default NetworkPolicies and service accounts are enforced |
| G10 | Observability proof | Logs, metrics, and traces capture correlation/request IDs across gateway, TSHEPO, service, DB/event path |

## G1: Envoy -> TSHEPO/OPA -> Service Enforcement

Acceptance evidence:

- Gateway route exists for a protected API.
- Direct service access from outside the cluster fails.
- Request without valid auth/context fails closed.
- Request with valid auth/context succeeds.
- TSHEPO/OPA decision is logged with request ID/correlation ID.
- Target service receives only gateway-mediated traffic.

Suggested checks:

```bash
kubectl -n impilo-gateway get gateway,httproute,service
kubectl -n impilo-trust logs deploy/tshepo-authz --tail=200
kubectl -n impilo-gateway logs deploy/envoy-gateway --tail=200
```

## G2: Mandatory Trust Headers

Mandatory headers:

```text
X-Tenant-ID
X-Pod-ID
X-Request-ID
X-Correlation-ID
X-Actor-ID
X-Actor-Type
X-Purpose-Of-Use
X-Assurance-Level
X-Access-Mode
```

Context headers required when applicable:

```text
X-Provider-ID
X-Facility-ID
X-Department-ID
X-Ward-ID
X-Workspace-ID
X-Programme-ID
X-Shift-ID
```

Acceptance evidence:

- Missing mandatory headers are rejected, or generated by a trusted gateway/session component.
- Header values are visible in structured logs where safe.
- Request ID and correlation ID propagate across gateway, TSHEPO, BFF, and backend service.

## G3: No Direct Public Service Exposure

Acceptance evidence:

- Public DNS resolves only to approved ingress/gateway endpoints.
- Backend services use ClusterIP/internal services unless explicitly approved.
- Database, Kafka, Redis, MinIO admin, Orthanc admin, Envoy admin, Prometheus, and Grafana are not public.

Suggested checks:

```bash
kubectl get svc -A
kubectl get ingress -A
kubectl get routes -A
kubectl get gateway,httproute -A
```

## G4: No UI-To-Database/Cache/Bus Access

Acceptance evidence:

- NetworkPolicy denies UI namespace egress to PostgreSQL, Redis, Kafka, object storage, and internal service ports except the gateway/BFF routes.
- UI applications call gateway or Experience BFF only.

Suggested checks:

```bash
kubectl -n impilo-experience get networkpolicy
kubectl -n impilo-experience exec deploy/one-ui-shell -- sh -c 'nc -zv postgres.impilo-data.svc 5432'
kubectl -n impilo-experience exec deploy/one-ui-shell -- sh -c 'nc -zv kafka.impilo-data.svc 9092'
```

The direct checks above should fail unless run from an explicitly approved diagnostic pod.

## G5: Per-Service Database Credentials

Acceptance evidence:

- Each service has its own database user.
- Service users can access only their own database/schema and required migration objects.
- Shared superuser credentials are not mounted into application pods.
- PgBouncer or connection pool limits are configured where used.

Suggested check:

```sql
select usename from pg_user order by usename;
```

For each service, verify that cross-service table access is denied.

## G6: Audit And Outbox Behaviour

Acceptance evidence:

- Protected create/update/delete workflows write audit events.
- Services with domain events have `event_outbox` or equivalent reliable publishing table.
- Kafka topics receive expected events after outbox publication.
- Outbox lag is measured and visible on dashboards.

Suggested checks:

```sql
select count(*) from event_outbox;
```

Verify outbox lag and Kafka consumer lag metrics in Prometheus/Grafana.

## G7: Synthetic-Only PII

Acceptance evidence:

- Dataset provenance record states synthetic data generator/source.
- No production database dump is restored into sandbox.
- Data generation process is repeatable.
- Any external adapter uses mock credentials and mock endpoints unless explicitly approved.

Acceptance statement:

```text
No real patient, provider, facility staff, payment, document, or image data is present in this sandbox.
```

## G8: FHIR/BUTANO PII Separation

Acceptance evidence:

- BUTANO/FHIR records are keyed by CPID or approved non-PII identifiers.
- PII attributes live in VITO/identity stores, not FHIR resources.
- FHIR searches cannot return raw demographic PII unless routed through approved policy and projection.
- Synthetic tests prove a patient clinical record can be found via policy-governed identity resolution without storing PII in BUTANO.

## G9: Namespace Security Boundaries

Acceptance evidence:

- Every namespace has default deny NetworkPolicy.
- Each workload has a dedicated service account.
- RBAC grants are least privilege.
- Secrets are namespace-scoped or mounted through an approved external secret mechanism.
- Admin consoles require VPN/management network access.

## G10: Observability Proof

Acceptance evidence:

- Gateway, TSHEPO, registry, clinical, BFF, and data services expose metrics.
- Structured logs include service, environment, request ID, correlation ID, and safe context identifiers.
- Traces cross at least one end-to-end workflow: UI/BFF -> gateway -> TSHEPO -> registry/clinical service -> database/outbox/Kafka.
- Dashboards show latency, error rate, saturation, Kafka lag, DB latency, Redis health, and authorization latency.

## Promotion Rule

A sandbox deployment cannot be marked data-centre accepted until all gates are either:

- Passed with linked evidence, or
- Explicitly waived by the platform owner with a dated risk acceptance and remediation deadline.

Waivers must not be used for:

- Real PII in sandbox.
- Public database/Kafka/Redis exposure.
- Bypassing Envoy/TSHEPO for protected APIs.
- Shared production credentials.
