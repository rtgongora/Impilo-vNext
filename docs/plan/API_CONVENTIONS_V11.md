# Impilo vNext — API Conventions (v1.1)

**Version**: 1.0
**Date**: 2026-02-14
**Scope**: All new services (Outstanding 27). Legacy services adopt gradually.

---

## 1. Routing Prefix

### 1.1 Rule

All new v1.1-native services MUST use the `/internal/v1/**` routing prefix for all REST endpoints.

```
/internal/v1/{resource}
/internal/v1/{resource}/{id}
/internal/v1/{resource}/{id}/{sub-resource}
```

### 1.2 Rationale

- `/internal/` signals that these are platform-internal APIs, not public-facing
- `/v1/` is the API version segment; incremented only on breaking changes
- Public-facing APIs (citizen portal, external integrations) are routed through the Experience Plane and NEVER call `/internal/` directly

### 1.3 Legacy Service Routes

Legacy services retain their existing route prefixes:

| Service | Current Prefix | Migration Plan |
|---|---|---|
| vito-service | `/api/v1/` | Retain; add `/internal/v1/` aliases for new v1.1 endpoints |
| pct-service | `/api/v1/journeys` | Retain; new endpoints use `/internal/v1/` |
| oros-service | `/v1/orders` | Retain; new endpoints use `/internal/v1/` |
| mushex-service | `/mushex/v1/` | Retain; new endpoints use `/internal/v1/` |
| msika-flow-service | `/msika-flow/v1/` | Retain; new endpoints use `/internal/v1/` |
| costing-engine-service | `/costa/v1/` | Retain; new endpoints use `/internal/v1/` |
| integration-hub | `/internal/v1/` | Already v1.1-native |
| notification-service | `/internal/v1/` | Already v1.1-native |
| rules-service | `/internal/v1/` | Already v1.1-native |

### 1.4 Envoy Route Configuration

New services are registered in `infra/envoy/envoy.yaml` with prefix matching:

```yaml

    prefix: "/internal/v1/providers"
  route:
    cluster: varapi_service
    timeout: 10s

- match:
    prefix: "/internal/v1/facilities"

    cluster: tuso_service
    timeout: 10s
```

## 2. Required Headers

### 2.1 Mandatory Request Headers

Every request to a v1.1-native service MUST include these four headers. Missing or blank headers result in `400 MISSING_REQUIRED_HEADER`.

| Header | Type | Description | Source |
|---|---|---|---|
| `X-Tenant-ID` | String (UUID or well-known) | Tenant (health authority) identifier | Injected by UI `apiClient.ts` or Envoy |
| `X-Pod-ID` | String | Pod identifier; `national-spine` for Level 1 | Injected by Envoy; default `national-spine` |
| `X-Request-ID` | String (UUID) | Unique per-request identifier for tracing | Generated by client or Envoy |
| `X-Correlation-ID` | String (UUID) | End-to-end correlation across services | Propagated from originating request |

### 2.2 Conditional Headers

| Header | When Required | Type | Description |
|---|---|---|---|
| `Idempotency-Key` | On POST, PUT, PATCH (command endpoints) | String (max 255) | Client-supplied deduplication key |
| `X-Client-Timeout-MS` | Optional | Integer | Client-requested timeout; service SHOULD honor |

### 2.3 Trust Headers (Injected by Envoy/TSHEPO)

These headers are set by the Envoy ext_authz filter after TSHEPO policy evaluation. Services read but NEVER set these.

| Header | Type | Description |
|---|---|---|
| `X-Actor-ID` | String | Authenticated actor identifier |
| `X-Actor-Type` | PROVIDER, OPERATOR, CITIZEN, SYSTEM | Actor category |
| `X-Purpose-Of-Use` | TREATMENT, PAYMENT, OPERATIONS, etc. | Declared purpose |
| `X-Device-Fingerprint` | SHA-256 hash | Device identity |
| `X-Facility-ID` | String (optional) | Facility scope |
| `X-Workspace-ID` | String (optional) | Workspace scope |
| `X-Shift-ID` | String (optional) | Duty shift scope |
| `X-Decision` | ALLOW, DENY, STEP_UP_REQUIRED | TSHEPO policy decision |
| `X-Obligations` | JSON | Policy obligations |
| `X-Max-Scope` | String | Data scope boundary |
| `X-Mask-Fields` | CSV | Fields to mask in response |
| `X-Logging-Level` | String | Audit level |
| `X-Consistency-Class` | A, B, C | Action safety classification |
| `X-Projection-Staleness-MS` | Integer | Projection staleness in milliseconds |
| `X-Decision-Evidence-ID` | UUID | Audit event reference for this decision |
| `X-Break-Glass` | Boolean | Whether break-glass is active |

### 2.4 Service-to-Service Headers

When one service calls another via RestTemplate/WebClient:

| Header | Source | Description |
|---|---|---|
| `X-Service-ID` | Calling service name | Identifies the calling service |
| `X-MTLS-Identity` | mTLS certificate subject | mTLS-based service identity |
| `X-Access-Mode` | `INTERNAL` | Always `INTERNAL` for S2S calls |

These are propagated by `TrustHeaderPropagator` from `libs/tshepo-sdk`.

### 2.5 Header Enforcement Implementation

The `tech-companion` library provides `HeaderEnforcementFilter` (auto-configured):

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
public class HeaderEnforcementFilter extends OncePerRequestFilter {

    private static final List<String> REQUIRED = List.of(
        "X-Tenant-ID", "X-Pod-ID", "X-Request-ID", "X-Correlation-ID"
    );

    @Override
    protected void doFilterInternal(HttpServletRequest req, ...) {
        for (String header : REQUIRED) {
            String value = req.getHeader(header);
            if (value == null || value.isBlank()) {
                writeErrorEnvelope(response, 400, "MISSING_REQUIRED_HEADER",
                    "Required header '" + header + "' is missing or blank",
                    req.getHeader("X-Request-ID"),
                    req.getHeader("X-Correlation-ID"));
                return;
            }
        }
        filterChain.doFilter(request, response);
    }
}
```

## 3. Error Envelope

### 3.1 Format

All error responses MUST use this canonical JSON structure:

```json
{
  "error": {
    "code": "MISSING_REQUIRED_HEADER",
    "message": "Required header 'X-Tenant-ID' is missing or blank",
    "details": "The X-Tenant-ID header must be present on all requests to identify the tenant context.",
    "request_id": "req-12345",
    "correlation_id": "corr-67890"
  }
}
```

### 3.2 Required Fields

| Field | Type | Description |
|---|---|---|
| `error.code` | String | Machine-readable error code (UPPER_SNAKE_CASE) |
| `error.message` | String | Human-readable error summary |
| `error.details` | String (nullable) | Additional context or remediation hints |
| `error.request_id` | String | Echo of `X-Request-ID` header (or generated if absent) |
| `error.correlation_id` | String | Echo of `X-Correlation-ID` header (or generated if absent) |

### 3.3 Standard Error Codes

| Code | HTTP Status | Description |
|---|---|---|
| `MISSING_REQUIRED_HEADER` | 400 | A mandatory header is missing or blank |
| `IDEMPOTENCY_KEY_REQUIRED` | 400 | POST/PUT/PATCH without `Idempotency-Key` |
| `IDENTITY_CONFLICT` | 409 | Same `Idempotency-Key` with different body |
| `FEDERATION_AUTHORITY_VIOLATION` | 403 | Non-national pod accessing national-only endpoint |
| `RESOURCE_NOT_FOUND` | 404 | Requested resource does not exist |
| `VALIDATION_ERROR` | 400 | Request body fails validation |
| `CONSISTENCY_CLASS_VIOLATION` | 403 | Class A check failed (sync Kernel unavailable) |
| `STALENESS_EXCEEDED` | 409 | Class B staleness threshold breached |
| `ENTITLEMENT_INVALID` | 403 | Class C offline entitlement invalid/expired |
| `STEP_UP_REQUIRED` | 403 | Operation requires step-up authentication |
| `BREAK_GLASS_REQUIRED` | 403 | Class A blocked; break-glass not active |
| `TENANT_MISMATCH` | 403 | Resource belongs to different tenant |
| `INTERNAL_ERROR` | 500 | Unexpected server error |

### 3.4 Error Envelope Implementation

The `tech-companion` library provides `ErrorEnvelopeExceptionHandler`:

```java
@RestControllerAdvice
public class ErrorEnvelopeExceptionHandler {

    @ExceptionHandler(ImpiloException.class)
    public ResponseEntity<Map<String, Object>> handle(ImpiloException ex, HttpServletRequest req) {
        Map<String, Object> error = Map.of(
            "code", ex.getCode(),
            "message", ex.getMessage(),
            "details", ex.getDetails(),
            "request_id", req.getHeader("X-Request-ID"),
            "correlation_id", req.getHeader("X-Correlation-ID")
        );
        return ResponseEntity.status(ex.getHttpStatus())
            .body(Map.of("error", error));
    }
}
```

## 4. Idempotency

### 4.1 Rule

Every POST, PUT, and PATCH request to a command endpoint MUST include the `Idempotency-Key` header. Missing it results in `400 IDEMPOTENCY_KEY_REQUIRED`.

### 4.2 Behavior Matrix

| Scenario | Response |
|---|---|
| First request with key K + body B | Execute operation, return result R, store (K, hash(B), R) |
| Repeat request with key K + same body B | Return stored result R (replay, no side effects) |
| Repeat request with key K + different body B' | Return `409 IDENTITY_CONFLICT` |
| Key K after TTL expiry (default 24h) | Treat as new request |

### 4.3 Storage

The `tech-companion` library provides two implementations:

- `JdbcIdempotencyRepository`: stores in `{service}_idempotency` table (production)
- `InMemoryIdempotencyRepository`: stores in ConcurrentHashMap (tests)

### 4.4 Idempotency Table Schema

```sql
CREATE TABLE {service}_idempotency (
    idempotency_key     VARCHAR(255) PRIMARY KEY,
    body_hash           VARCHAR(64) NOT NULL,
    response_status     INTEGER NOT NULL,
    response_body       JSONB,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at          TIMESTAMPTZ NOT NULL DEFAULT NOW() + INTERVAL '24 hours'
);

CREATE INDEX idx_{service}_idem_expires ON {service}_idempotency (expires_at);
```

### 4.5 Exempt Endpoints

GET and DELETE endpoints are exempt from idempotency requirements:
- GET is inherently idempotent (safe, read-only)
- DELETE is inherently idempotent (deleting twice produces same state)

Snapshot endpoints (`GET /internal/v1/{resource}/snapshot`) are also exempt.

## 5. Federation Authority

### 5.1 Rule

Certain endpoints are restricted to `national-spine` pod only. Requests from non-national pods receive `403 FEDERATION_AUTHORITY_VIOLATION`.

### 5.2 Annotation

```java
@NationalOnly  // Custom annotation from tech-companion
@PostMapping("/internal/v1/rules")
public ResponseEntity<?> createRule(@RequestBody RuleDto dto) { ... }
```

### 5.3 Behavior

| Pod ID | Endpoint Restriction | Result |
|---|---|---|
| `national-spine` or `national` | Any | Allowed |
| Any other pod ID | `@NationalOnly` endpoint | 403 |
| Any other pod ID | Non-restricted endpoint | Allowed |

### 5.4 Implementation

The `tech-companion` library provides `FederationAuthorityInterceptor`:

```java
@Component
public class FederationAuthorityInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (handler instanceof HandlerMethod hm && hm.hasMethodAnnotation(NationalOnly.class)) {
            String podId = req.getHeader("X-Pod-ID");
            if (podId != null && !podId.equals("national-spine") && !podId.equals("national")) {
                writeErrorEnvelope(res, 403, "FEDERATION_AUTHORITY_VIOLATION", ...);
                return false;
            }
        }
        return true;
    }
}
```

## 6. Request/Response Conventions

### 6.1 Success Response (Single Resource)

```json
{
  "data": {
    "id": "uuid-or-ulid",
    "type": "Provider",
    "attributes": { ... }
  },
  "meta": {
    "request_id": "req-12345",
    "correlation_id": "corr-67890"
  }
}
```

### 6.2 Success Response (Collection)

```json
{
  "data": [
    { "id": "...", "type": "Provider", "attributes": { ... } }
  ],
  "meta": {
    "request_id": "req-12345",
    "correlation_id": "corr-67890",
    "page": {
      "number": 0,
      "size": 20,
      "total_elements": 142,
      "total_pages": 8
    }
  }
}
```

### 6.3 Content-Type

All requests and responses use `application/json` unless explicitly documented otherwise (e.g., FHIR endpoints use `application/fhir+json`).

### 6.4 HTTP Methods

| Method | Semantics | Idempotency-Key | Body |
|---|---|---|---|
| GET | Read resource(s) | Not required | No body |
| POST | Create resource or execute command | Required | JSON body |
| PUT | Full resource replacement | Required | JSON body |
| PATCH | Partial resource update | Required | JSON body (partial) |
| DELETE | Remove resource | Not required | Optional reason body |

### 6.5 HTTP Status Codes

| Code | Usage |
|---|---|
| 200 | Successful read, update, or idempotent replay |
| 201 | Successful resource creation |
| 204 | Successful delete (no body) |
| 400 | Validation error, missing header, missing idempotency key |
| 403 | Authorization failure, federation violation, consistency class violation |
| 404 | Resource not found |
| 409 | Idempotency conflict, state conflict |
| 500 | Unexpected server error |

## 7. Timeout Propagation

### 7.1 Rule

If a client sends `X-Client-Timeout-MS`, the service SHOULD honor it by setting an internal deadline. If the operation cannot complete before the deadline, it SHOULD return `504 Gateway Timeout` rather than leaving the client hanging.

### 7.2 Implementation

The `tech-companion` library provides `TimeoutFilter`:

```java
@Component
public class TimeoutFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, ...) {
        String timeoutMs = req.getHeader("X-Client-Timeout-MS");
        if (timeoutMs != null) {
            long deadline = System.currentTimeMillis() + Long.parseLong(timeoutMs);
            RequestContext.current().setDeadline(deadline);
        }
        filterChain.doFilter(request, response);
    }
}
```

Services check `RequestContext.current().isExpired()` before starting expensive operations.

## 8. API Versioning Policy

### 8.1 URL Versioning

The API version is part of the URL path: `/internal/v1/`. When a breaking change is required:

1. Create `/internal/v2/` endpoints with new behavior
2. Mark `/internal/v1/` endpoints as deprecated (respond with `Deprecation` header)
3. Support both versions for 2 release cycles
4. Remove `/internal/v1/` after migration period

### 8.2 Breaking vs Non-Breaking Changes

| Change | Breaking? | Action Required |
|---|---|---|
| Add optional query parameter | No | Deploy freely |
| Add optional response field | No | Deploy freely |
| Add new endpoint | No | Deploy freely |
| Remove response field | Yes | Version bump |
| Change field type | Yes | Version bump |
| Remove endpoint | Yes | Deprecate first, then version bump |
| Change required header | Yes | Version bump |
| Change error code for same condition | Yes | Version bump |

### 8.3 Deprecation Header

```
Deprecation: true
Sunset: Sat, 01 Aug 2026 00:00:00 GMT
Link: </internal/v2/providers>; rel="successor-version"
```
