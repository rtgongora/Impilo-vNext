# Nompilo mobile implementation notes

Nompilo is the Impilo AI assistant / helpdesk companion. On mobile it must
feel like a **warm, non-intrusive guide**, not a clinical decision system.

## SDK surface

`apps/mobile/packages/mobile-nompilo` exposes:

- `nompiloClient.ask(request)` — calls the BFF LLM gateway
  (`/internal/v1/llm/chat`).
- `useNompilo({ context, seed })` — React hook that manages conversation
  state, role-aware system prompt, and the fallback.
- `NOMPILO_DISCLAIMER` — the user-facing disclaimer chip.
- Role types: `PROVIDER`, `CITIZEN`, `COURIER`, `SUPERVISOR`, `OUTREACH`, `ADMIN`.

## Mobile entry points

| Surface | Where |
| --- | --- |
| Citizen app — global launcher | `AppNavigator` floats a `NompiloLauncher` always-on, bottom-right. |
| Citizen app — modal | `NompiloAssistantScreen` inside a `BottomSheet`, opened by the launcher. |
| Provider app — global launcher | Same as citizen, accent-coloured `#009739`. |
| Provider app — modal | `NompiloAssistantScreen` (provider variant). Role is derived from `mode` (PROVIDER / COURIER / SUPERVISOR / OUTREACH). |
| Provider app — contextual help | Future: small `?` button on complex screens (encounter, dispatch, claims). Tracked as a follow-up. |

## Fallback behaviour

If the LLM gateway is unreachable or returns an error:

1. The SDK falls back to a deterministic, role-aware response generated by
   `fallback.ts`. This is **never** clinical advice — it always points to a
   safe next step (find a clinic, open the appointments tab, contact
   support).
2. The mobile screen shows a yellow warning banner: *"Assistant model is
   unavailable. I'll reply with simple guidance until it's back."*
3. The fallback flag `lastResult.usedFallback` is exposed so screens can
   adjust copy.

The fallback is **not** allowed to invent:

- Clinical decisions
- Drug recommendations
- Financial / payment advice
- Personal patient data

## Disclaimer

Every Nompilo screen renders the badge **Decision support only** + the
disclaimer string `NOMPILO_DISCLAIMER`:

> Nompilo is a decision-support assistant. Verify any clinical or financial
> guidance with a qualified professional before acting.

This is enforced in both citizen and provider variants regardless of
whether the LLM is online.

## Role-aware prompting

`useNompilo` derives the system prompt from `context.role`:

- `PROVIDER` — clinical tone, no patient-specific data unless the actor
  context includes a treatment purpose-of-use.
- `CITIZEN` — warm tone, short sentences, signpost to the right screen
  rather than answering medical questions.
- `COURIER` — operational tone, focused on dispatch / proof / handover.
- `SUPERVISOR` — managerial tone, policy and workflow guidance.
- `OUTREACH` — field-worker tone, screening and follow-up guidance.

## Privacy

- The mobile SDK never sends patient identifiers, vital signs or chart text
  to the LLM gateway unless the user explicitly pasted them. The
  conversation buffer stays in-memory only — it is not persisted in offline
  storage.
- The gateway path goes through Tshepo via the BFF (`assertGovernedRead`),
  so even server-side the LLM call honours actor + purpose-of-use.
- Voice / dictation input is **not** wired in this wave; the input field
  uses the OS keyboard. Adding voice is a future task and must respect the
  same privacy boundaries.

## Banned patterns

- ❌ Hardcoded "fake AI" responses that masquerade as real LLM output.
- ❌ Suggesting medications, dosages, dispensing decisions or clinical
  judgements.
- ❌ Storing the user's chat history in offline / SQLite cache.
- ❌ Sending patient-record content to the LLM without a treatment
  purpose-of-use.
