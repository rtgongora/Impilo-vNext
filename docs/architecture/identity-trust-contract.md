# Impilo Identity Contract

**Status:** RATIFIED (PO decision record, 2026-07-18) — implementation verdict **AMBER** until the §16 journey pack runs green.
**Owner:** Identity Trust Core governance (trust plane).
**Supersedes / corrects:** the identifier statements in `docs/experience/EXPERIENCE_DOCTRINE_IMPILO_IDENTITY.md` and `docs/vito/VITO_AND_IMPILO_IDENTITY.md` (both previously conflated distinct identifiers — see §17); the legacy PHID SOP identifier chapter (format retained for legacy aliases only, §5).

This is the single normative contract for person identifiers, their generation, persistence, resolution, and trust semantics across Impilo vNext. Where any other document disagrees with this contract, this contract wins and the other document must be corrected.

---

## 1. The four-identifier naming contract (D1)

| Identifier | Meaning | Format | Generated by | Who may see / store it |
|---|---|---|---|---|
| **Impilo ID** | Patient-held health identifier (alias) | §4 (human-friendly, check-charactered) | VITO issuer module, at issuance approval | Client, app, card, QR, registration staff. Public copy: **"Impilo ID"** / **"Impilo Health ID"** |
| **HID** (Health ID) | Canonical internal health identity anchor | UUIDv4 | VITO issuer module, at registration | Identity Trust Core only (§3). Never clinical services, never the browser |
| **CRID** | Client-registry demographic-record identifier (record lineage / merge anchor) | UUIDv4 | VITO | Identity services and authorised identity workflows only |
| **CPID** | Pseudonymous clinical-subject identifier | **Independent random UUIDv4** | tshepo-identity, via `id_mapping` | Clinical services (SHR/BUTANO, PCT, inpatient, pharmacy, OROS, MADI, surveillance, safety, booking) only |

Supporting identifiers:

| Identifier | Meaning | Rule |
|---|---|---|
| **O-CPID** | Offline provisional clinical-subject identifier | Random UUIDv4, minted by tshepo-identity (`provisional_cpid`); reconciled to a canonical CPID on sync (§8) |
| **DID** (`did:impilo:…`) | Cryptographic machine credential anchor | SHA-256 over HID + entropy; carried on cards/QR, never a lookup key for clinical data |
| **Card serial / card number** | Physical/virtual credential instance | `IMP-YYYY-XXXXXXXX`; revocable independently of every identifier above (§10) |
| **Legacy PHID** | Historical MRS identifier | Governed alias, permanently valid (§5) |

**Hard rules:**

- The public is taught exactly one identifier: the **Impilo ID**. HID, CRID, CPID, database ids, and FHIR resource ids are never client-facing.
- **CPID is never derived** — not from HID, not from CRID, not from tenant + anything. The only link is the `tshepo_identity.id_mapping` row.
- Nothing except tshepo-identity holds HID and CPID at the same time. The experience BFF may hold both **transiently** as a composition tier (patient banner + clinical timeline) but never persists either and never emits either to a client (§12).
- The browser receives neither HID, CRID, nor CPID — only a short-lived Patient Context Token and authorised display data (§12).
- Actor/worker identity (providers, staff — Varapi `impilo_health_id`, Vashandi, Tuso assignment rows) is **identity-plane** usage of the HID and is out of scope for CPID rules. Patient *clinical-subject* keys are the CPID's exclusive domain.

## 2. Governance stance: Issuer and Resolver, not a black box (D2)

The identifier machinery is a governed **Identity Credential Issuer and Resolver**. It is centrally operated and access-restricted, but it is **not opaque**:

- Every algorithm (formats, check characters, hashing, encryption, token signing) is specified in this contract with published test vectors.
- All generation/validation code is independently testable (unit-test vectors in §4/§5 are normative).
- Key material lives behind the tshepo-keys custody path (HSM/managed key service target), versioned; no service self-generates long-lived signing keys (§10 QR rule).
- Every issuance, resolution, merge, revocation, and reverse lookup is audited (outbox events).
- Formats are versioned; already-issued identifiers remain valid across format versions forever.

## 3. The Identity Trust Core: logical plane, two physical components (D2)

```text
                        CITIZEN

                           │
                           ▼
        ┌─────────────────────────────────────────┐
        │        IDENTITY TRUST CORE (logical)     │
        │                                          │
        │  tshepo-identity-service                 │
        │   · CPID mint + id_mapping (sole HID↔CPID link)
        │   · resolution (alias-hash → HID → CPID) │
        │   · scoped tokens / Patient Context Token│
        │   · O-CPID lifecycle                     │
        │   · SubjectTranslationRelay (event plane)│
        │                                          │
        │  VITO issuer module                      │
        │   · HID + CRID + DID mint                │
        │   · Impilo ID issuance + alias vault     │
        │   · legacy PHID registry + pools         │
        │   · card lifecycle + signed QR           │
        └───────────┬──────────────────┬───────────┘
                    ▼                  ▼
         VITO CLIENT REGISTRY      BUTANO SHR + clinical services
         CRID + demographic PII    CPID + clinical data
         matching / dedup cases    no matching, no PII (enforced)
                    │
                    ▼
              ABIS SERVICE (§11)

```

Both physical components operate under single trust-core governance (this contract). The split is ratified: relocating issuance into tshepo services is explicitly rejected — VITO must hold the HID regardless, and the privacy boundary is enforced by *what may co-reside* (only tshepo-identity sees HID+CPID together), not by service count.

## 4. Impilo ID format

### 4.1 Format v2 — ratified for national issuance (D8)

The as-built v1 format (§4.2) is **not ratified** for national issuance. Format v2:

- **Structure:** `DDDDDDDDDC` — 9 random digits + 1 **ISO 7064 MOD 11,10** check digit. 10 characters, all numeric.
- **Space:** 10⁹ base combinations (~41× the legacy SOP's 24 M), before any future length extension.
- **Check scheme:** ISO 7064 MOD 11,10 (hybrid system) — an internationally specified algorithm (the German tax-ID scheme) detecting **100 % of single-character substitutions and 100 % of adjacent transpositions** (verified against the vectors below). This replaces v1's ad-hoc weighted mod-24 letter, which was never formally specified and mixes alphabets.
- **Why all-numeric:** verbal relay, phone keypads, USSD, elderly-friendly transcription; no ambiguous letters at all (stronger than excluding I/O).
- **No semantic encoding:** no facility, province, birth year, sex, citizenship, or issuance date is derivable from the value.
- **Display grouping:** `123 456 789 7` (3-3-3-1); normalisation strips all whitespace/hyphens before validation.
- **Format version:** issuance records carry `format_version = 2`. Validation accepts v1 and v2 (and legacy PHID as an alias class); **issuance** is v2-only once implemented.
- **Persistence:** per §6 — never plaintext.

**ISO 7064 MOD 11,10 algorithm (normative):**

```text
p ← 10
for each digit d of the 9-digit body, left to right:
    s ← (d + p) mod 10;  if s = 0 then s ← 10
    p ← (2·s) mod 11
check ← 11 − p;  if check = 10 then check ← 0
```

**Test vectors (v2):**

| Body | Full Impilo ID | Valid? |
|---|---|---|
| `123456789` | `1234567897` | ✔ |
| `000000000` | `0000000006` | ✔ |
| `987654321` | `9876543213` | ✔ |
| `555019273` | `5550192737` | ✔ |
| `400072186` | `4000721866` | ✔ |
| — | `1234567890` | ✘ (bad check) |
| — | `1243567897` | ✘ (transposition detected) |

### 4.2 Format v1 — as-built, deprecated for issuance

`#########X` — 9 digits + 1 check **letter** = weighted positional sum mod 24 (weights `2,3,4,5,6,7,8,9,2`, alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ`, I/O excluded). Implemented in `vito-service .../core/id/ImpiloIdFormat.java`. Retained only to validate any v1-issued preview IDs; the preview estate is wiped at the CPID cutover, so v1 values should not survive into national issuance.

**Test vectors (v1):** `123456789` → `123456789U`; `000000000` → `000000000A`; `987654321` → `987654321L`; `555019273` → `555019273H`; `400072186` → `400072186N`.

## 5. Legacy PHID — permanent governed alias (D10)

### 5.1 Format (from the MRS SOP, as implemented in `LegacyPhidFormat.java`)

`DDD L DDD C` (8 chars): 3 digits, 1 letter (A–Z excluding I/O), 3 digits, 1 check digit = `(10 − (sum of the six digits mod 10)) mod 10`. Regex `^[0-9]{3}[A-HJ-NP-Z][0-9]{3}[0-9]$`. Note: this is a plain digit-sum mod-10, **not Luhn** (the SOP's Luhn description was never implementable for the letter position and is corrected here).

**Test vectors:** `123A456` → `123A4569`; `000A000` → `000A0000`; `999Z999` → `999Z9996`; `735K208` → `735K2085`.

### 5.2 Alias doctrine

- Every **assigned** legacy PHID becomes an alias: `alias_type = LEGACY_PHID`, canonical identity = HID, status ∈ `ACTIVE | MERGED | DISPUTED | REVOKED`.
- A person may hold several historical aliases; exactly one canonical HID. Migration into vNext **never** issues a new public identifier merely because the person migrated.
- Merged aliases **redirect** to the survivor HID; they are never deleted.
- `DISPUTED` (same PHID observed against two people) blocks resolution and routes to the dedup steward queue; it never auto-resolves.
- **Unassigned/preallocated pool numbers are not aliases.** They are recorded in `phid_pool` with status `RESERVED | UNUSED | EXPIRED | RETIRED` so they can never be accidentally issued or claimed.
- Import provenance is mandatory: source facility, source system, issuance date, migration batch, reconciliation decision.

## 6. Impilo ID persistence doctrine (D3)

> The Impilo ID must never be stored in plaintext anywhere. Within the Identity Trust Core it is held either as a keyed cryptographic derivation (Pattern A) or as an encrypted alias registry entry with a protected hashed lookup index (Pattern B). Outside the Trust Core it is never persisted at all — services and UIs receive it transiently for display/print only.

| Pattern | Mechanism | Applies to |
|---|---|---|
| **A — Deterministic cryptographic alias** | Impilo ID regenerable from HID + key-version via a keyed format-preserving derivation; no stored value needed | Permitted for **new v2 issuance** if adopted at C2 implementation review; requires HSM-custodied key + version column |
| **B — Secure alias registry** | AES-256-GCM-encrypted credential (key via tshepo-keys custody, key-version column) + lookup index = `HMAC-SHA256(pepper, normalised id)` + verifier = Argon2id | **Required** for legacy PHIDs, imported external identifiers, governed replacements, and any alias that cannot be regenerated. Default for v2 issuance unless Pattern A is adopted |

The existing `vito.identity_alias` double-hash vault is the Pattern B lookup index and is retained unchanged. The plaintext columns `vito.client.impilo_id` and `vito.issuance_requests.impilo_id_issued` are **contract violations** and are removed (Wave C1). Recovery, same-number card reissue, and issuance investigation are served by Pattern B decryption (audited) or Pattern A regeneration — never by a plaintext column.

## 7. CPID and the resolution pattern (D1)

### 7.1 The one rule

> A clinical service only ever receives a CPID, and every CPID it receives was minted or resolved by the Identity Trust Core. Nothing except tshepo-identity holds HID and CPID at the same time. The browser holds neither.

### 7.2 Synchronous path (request-scoped)

1. The orchestrator owning patient context (experience-bff, or a clinical service in a system flow) resolves the person via tshepo-identity (`POST /v1/identity/resolve` for presented credentials; mapping lookup where it legitimately holds an HID because it is identity-plane).
2. tshepo-identity returns the CPID and issues a **patient-context scoped token** (`TokenIssuanceService`: `sub_ref = CPID`, scope `patient-context`, target service, TTL 300 s, EdDSA-signed via tshepo-keys).
3. Downstream clinical calls carry `X-Subject-ID: <cpid>` plus the token. Clinical services verify signature and `sub_ref == X-Subject-ID` (`SubjectContextFilter`); possession of a valid token **is** the structural proof the CPID came from the translator.
4. Unknown-patient (trauma/mass-casualty) mint: clinical callers use tshepo-identity `POST /v1/identity/subjects/provisional`, which orchestrates the VITO mint internally and returns `{cpid, status}` — the HID never transits to the clinical caller. VITO's `/internal/v1/identities/provisional` accepts only the tshepo-identity service identity.

### 7.3 Asynchronous path (event plane)

- VITO emits identity-plane events (HID-keyed) on `impilo.vito.identity` / `impilo.vito.dedup` — these topics are **identity-plane only** (legitimate consumers: ndila address sync, identity tooling).
- The **SubjectTranslationRelay** (inside tshepo-identity) consumes them, resolves HID→CPID via `findOrCreateMapping`, strips HID and all PII, and re-emits clinical-plane events on `impilo.identity.subject.{created,verified,deceased,merged,merge_reversed,reconciled}.v1`, partitioned by CPID. Schemas declare `additionalProperties: false` with **no health_id property** — the invariant is contract-testable.
- Clinical services subscribe **only** to `impilo.identity.subject.*`. Topic namespace = plane boundary.
- Merge: the relay emits `{survivor_cpid, merged_cpid}` and marks the merged `id_mapping` row `RETIRED` with `merged_into_cpid` — future resolutions of the merged HID return the survivor CPID (redirect, never delete).

### 7.4 Reverse resolution

`GET /v1/identity/mappings/by-cpid/{cpid}` exists for authorised composition flows (e.g. deep-link entry with only a CPID). It requires scope `identity:reverse-resolve` + `X-Purpose-Of-Use`, and every call is audited via an outbox event. There is no unaudited reverse path.

## 8. Offline: O-CPID

- Issued by tshepo-identity (`POST /v1/identity/cpid/provisional`) via tshepo-offline-service when a device cannot reach the estate; random UUIDv4, facility- and device-attributed, status `PROVISIONAL`.
- On reconnection, the sync path registers/matches the person (VITO), then reconciles: canonical CPID minted via `findOrCreateMapping`, provisional row marked `RECONCILED` with `canonical_cpid`, and `impilo.identity.subject.reconciled.v1 {provisional_cpid, canonical_cpid}` is emitted. Clinical services repoint exactly as for merges (same `IdentityRepointHook` machinery; BUTANO reference rewrite).
- Offline registration must never silently create a permanent duplicate: if the person already exists, reconciliation returns the existing CPID and flags the provisional as duplicate.

## 9. Assurance is a four-dimension vector (D5)

A single trust number (the ideation's T0–T4) is rejected as too coarse. Access decisions evaluate four independent dimensions, combined at decision time with consent/legal basis, purpose of use, and data sensitivity:

| Dimension | Question | Source of truth |
|---|---|---|
| **IAL — identity proofing** | How confidently do we know who this person is? | identity-assurance-service LOA1–4 + VITO `ClientVerificationState` / proofing events |
| **AAL — authentication** | How strongly did they authenticate this session? | Keycloak ACR / eSignet + step-up (TOTP/OTP/passkey) via tshepo-authz session assurance |
| **RLC — record-link confidence** | How confidently is this account linked to the correct HID? | match disposition (AUTO_LINKED / MANUAL_LINKED / PENDING / DISPUTED) + `client_authorization_link` evidence |
| **SDA — session/device assurance** | Is the current device and session sufficiently trusted? | identity-assurance attestations (device binding, risk score) |

Rules:

- A step-up decision must name the **deficient dimension** (e.g. "authentication too weak for this action" vs "record link disputed") — they have different remedies.
- Strong proofing never compensates for a weak session, and vice versa.
- Emergency care is never denied for missing identity or failed assurance (care-first doctrine); emergency access is reason-coded and audited instead.
- The gateway's **R0–R5** ladder remains the citizen-facing UX vocabulary; each rung maps to minimum values of the four dimensions (crosswalk maintained in `docs/doctrine/health-services-gateway-doctrine.md` §4, extended for RLC/SDA). T0–T4 from the ideation is explanatory prose only — it is not implemented.

## 10. Cards and QR: credential, not identity

- The card carries: human-readable Impilo ID, card serial, signed QR (Ed25519 JWS whose `pointer` is an HMAC of the ID — never the plaintext), optional contactless token, emergency instructions. It never carries HID, CRID, CPID, national ID, or unencrypted clinical/demographic data.
- Losing a card revokes the **card credential** (serial/token), never the HID; the same Impilo ID is reissued after verification. All cards ever issued remain in the audit chain (`previous_card_id`).
- **Key custody rule:** no service self-generates long-lived signing keys at startup. The VITO QR signing key moves behind the tshepo-keys custody path (Wave C3); tokens must survive restarts and verify cross-instance.

## 11. Biometrics: dedicated ABIS boundary (D6)

```text
VITO — consent, biometric status, opaque reference (no templates)
  │
  ▼
ABIS service — protected (encrypted) templates, per-modality engines
  │
  ▼
TSHEPO — verified biometric subject → HID mapping
```

- Biometric templates do **not** live in the client registry: template custody moves from `vito.biometric_template` to a dedicated ABIS service (Wave E1). VITO retains consent, status, quality metadata, and an opaque template reference.
- **1:1 verification** is the routine operation (after a candidate is identified). **1:N identification** is restricted to enrolment, recovery, and deduplication — and a 1:N result yields **candidates for adjudication, never an automatic merge**.
- Matching thresholds are approved **per modality** (fingerprint / face / iris) and versioned with the algorithm.
- Every operation records consent reference, device, operator, template quality, algorithm version. Policy evaluation (Tshepo biometric-policy) precedes every operation; the engine remains **fail-closed** when no vendor matcher is configured.
- Exception paths (children, injuries, worn prints, disability, refusal, device failure) are first-class; biometric failure never blocks urgent care.
- The SHR never receives biometric templates or biometric identifiers.

## 12. The browser boundary: Patient Context Token (D7)

- After the trust core resolves a presented credential, the client (browser/mobile) receives a **short-lived Patient Context Token** (opaque reference) plus authorised display data (name for the banner, masked identifiers as policy allows).
- The BFF keeps the HID↔CPID pair server-side in the context session; UI routes and API responses to the client must not contain raw HID, CRID, or CPID values. (The Impilo ID may be displayed where the journey requires it — it is the client-facing identifier.)
- Response-shape guard tests enforce this at the BFF (Wave B5).

## 13. Matching, deduplication, merge

- VITO owns matching and deduplication; the SHR never matches (`PiiPreventionInterceptor` keeps it structurally incapable — no demographics ever arrive).
- Pipeline: exact identifier (Impilo ID / legacy PHID / NID / passport) → exact demographic → probabilistic (thresholds: auto-link ≥ 0.95, manual review ≥ 0.70) → biometric (ABIS, candidates only) → steward adjudication → audited merge/unmerge with reversible field decisions.
- One scoring implementation: `MatchingEngine` is the sole scorer (Wave C6 removes the duplicated copy in the external-registration path).
- Merge semantics ripple by contract: VITO merge event → relay `subject.merged` → clinical repoint (BUTANO rewrite + `IdentityRepointHook` dispatchers) → mapping RETIRED redirect.

## 14. Legacy PHID migration rules

1. Import all issued PHIDs (PHID server, central EHR, offline facilities) as `LEGACY_PHID` aliases per §5.2; match each to the correct VITO person; mint HID/CRID/CPID where absent.
2. Import preallocated pools separately into `phid_pool` as `RESERVED/UNUSED/EXPIRED/RETIRED` (§5.2) — never as aliases.
3. Quarantine same-PHID-two-people conflicts to the dedup steward queue (`DISPUTED`).
4. Never issue a second public identifier because a person enters vNext; the legacy PHID remains their working Impilo-class alias until they are issued a v2 Impilo ID through a governed journey (replacement, card issuance), and even then the PHID stays valid.
5. Full provenance per imported row (§5.2).

## 15. Pseudonymised, not anonymised

The operational SHR is **pseudonymised**: CPID separation is privacy-preserving but reversible through the authorised, audited trust-core workflow (§7.4). It must never be described as "anonymised" or "de-identified".

Analytics/research datasets require a **separate de-identification pipeline** (dataset-specific tokens — never the CPID itself, direct-identifier removal, quasi-identifier reduction, small-cell suppression, approved-policy gating), designed in Wave E4. Until that pipeline exists, downstream stores (NDR, warehouse) must not claim de-identification.

## 16. Conformance: the executable journey pack (the GREEN bar)

The implementation verdict flips AMBER→GREEN only when `tests/identity-contract/` runs these journeys green against the live estate (wired into full-boot post-deploy checks; results in `reports/identity-contract/`):

1. New registration → proofing → issuance (Impilo ID v2 appears only after approval; browser payload contains no internal IDs).
2. Returning client by Impilo ID (hash-chain resolution; plaintext never transits or persists).
3. Returning client by legacy PHID (alias statuses honoured; DISPUTED blocks to steward).
4. Recovery without the card (step-up gated, anti-enumeration).
5. Self-service record claiming (RLC dimension recorded).
6. Lost-card replacement (card token revoked, HID untouched, same Impilo ID reissued, chain audited).
7. Biometric enrolment + 1:1 verification via the ABIS boundary (consent-gated; 1:N yields candidates; care not blocked on engine unavailability).
8. Duplicate detection → merge → unmerge (thresholds, relay event, SHR rewrite, mapping redirect).
9. O-CPID issue → reconcile → clinical repoint.
10. Split retrieval: demographics via HID→VITO, clinical history via CPID→PCT/BUTANO; neither service received the other's key; the browser saw only the context token.
11. Assurance-vector escalation: raising one dimension changes the policy outcome end-to-end; step-up names the deficient dimension.
12. No-PII-reaches-SHR proof: PII-bearing writes and HID-keyed events are rejected/dropped; estate audit shows no `health_id` value present in any clinical database.
