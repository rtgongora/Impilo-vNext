# Lovable Absorption Matrix — Provider / Clinical / Place

**Source inspected:** Lovable reference prototype (Vite + React + TS + Supabase), cloned at
`scratchpad/impilo-structure/`.
**Scope:** UX / journey idea-mining only. The prototype is NOT judged as production. It is single-tenant,
has no Envoy/TSHEPO trust layer, no SoR separation (one flat Supabase schema of ~107 migrations owns *everything*
— patients, claims, FHIR resources, audit, terminology all in one DB), and several flows are mock-backed or
clinically out of sequence. Where that matters it is flagged.

**Honesty notes that recur below:**
- Most *hubs* (`MyProfessionalHub`, `PersonalHub`) use inline `mockXxx` arrays. Most *workspace/clinical* hooks
  (76 of 79 hooks) actually call Supabase, so the data layer is real-ish but single-tenant and PII-co-located.
- The prototype collapses VITO/BUTANO/TUSO/VARAPI/MUSHEX/COSTA into Supabase tables (`butano_fhir_resources`,
  `tuso_*`, `vito patients`, etc.) — it *simulates* the service mesh in one DB. vNext must not absorb that topology,
  only the UX it produces.
- vNext (`ui/one-ui-shell`) already has: a DB/API-backed `cadreEngine.ts` (richer than Lovable's), queue lanes
  (`triage`, `waiting`, `walk-in`, `scheduled`, `incoming-referrals`, `search`), beds, ward-board, workspace `[id]`
  + `[specialty]`, encounter, discharge, charge-sheet, referrals. So a lot here is *adapt/confirm*, not *adopt-new*.

## What Lovable ignores that vNext already has (do not regress)

- **Multi-tenant trust** (X-Tenant-ID/X-Pod-ID, Envoy ext_authz → Tshepo). Lovable has none; auth is a client route guard.
- **System-of-record separation** (VITO PII / BUTANO SHR CPID-only / MUSHEX claims / COSTA cost / ZIBO terminology /
  UBOMI CRVS / VARAPI provider / TUSO facility-affiliation). Lovable co-locates all of it in one Supabase DB.
- **Access/compensation as governed domains.** Lovable surfaces charges/pricing/wallet but owns them in the same EHR
  DB; vNext correctly splits COSTA / MUSHEX / coverage.
- **Auditable, non-overriding guidance (Nompilo).** Lovable's AI nudges ("recommended next", AI Diagnostic Assistant)
  are presentational; vNext requires guidance to be auditable and never override provider judgement.
- **Cadre scope-of-practice as policy** (`cadre_scope_rules`: allowed/supervised/blocked, facility-level-minimum).
  vNext's `cadreEngine` already encodes this; Lovable's cadre logic is form-visibility only, no enforcement.
