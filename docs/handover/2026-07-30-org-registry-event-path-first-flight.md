## Why it matters

Two consumers now depend on `impilo.org-registry.events` and neither has ever received a message:

1. **`RegulatoryAppointmentEndedTokenConsumer`** (tshepo-identity, RB-1) — revokes a regulator's
   duty token when their appointment ends. **Security-critical**: if it does not run, a revoked
   regulator keeps working until the 15-minute TTL expires on its own.
2. **`ConfigReleaseActivatedListener`** (varapi, NCZ #97) — reconciles a council's registers from
   its activated configuration. **Recoverable**: the operator endpoints
   `POST /v1/internal/councils/{councilId}/registers/reconcile` and
   `POST /v1/internal/organizations/{organizationId}/registers/reconcile` (shell:
   `/work/regulatory/[orgId]/registers`) do the same work, and the reconcile is idempotent.
   UI completeness for that surface landed 2026-07-31 — see
   [`2026-07-31-ncz-register-materialiser-and-regulatory-ui.md`](2026-07-31-ncz-register-materialiser-and-regulatory-ui.md).
   First-flight of the **event** path remains open until outbox rows appear after an activation.

Both are "wired" only in the sense that the code compiles and its unit tests pass. A topic carrying
zero traffic cannot distinguish a working consumer from a broken one, and both failure modes are
silent: nothing throws, and the estate looks identical to one where nobody activated anything.

## The ask

Include `organization-registry-service`, `varapi-service` and `tshepo-identity-service` in the next
deploy slot — behind the queued five-service FCV deploy, which carries live security fixes — then
run one first-flight check per consumer before either is treated as covered.

**Check A — configuration activation reconciles registers**

Activate a configuration release, then assert both halves:

```sql
-- the event was published, not merely written
select event_type, published_at, publish_error
  from org_registry.event_outbox
 where aggregate_type = 'REGULATORY_CONFIG_RELEASE';

-- and it caused the reconcile
select register_code, source, config_definition_key, config_semantic_version
  from varapi.professional_registers
 where council_id = :council and source = 'CONFIG_PACK';
```

**Check B — ending an appointment tears down the session**

End a regulatory appointment and assert the holder's `WORK_CONTEXT` token is revoked **before** its
15-minute TTL, not merely that it eventually expires.

## Deploy caveat

varapi `V039`–`V043` have never been applied by Flyway in any environment. They were validated with
`BEGIN…ROLLBACK` against the live preview databases and applied by runtime-proof rigs against
throwaway Postgres. **The first real Flyway run will be this deploy.** Verify the migrations are
inside the built jar before the redeploy — Flyway table-name typos only surface on live migration.

## Related stale claim

`OrgRegistryOutboxNoKafkaDrainer`'s Javadoc states its drainer swallows appointment-ended events "in
every environment that runs with the default (false, including preview today)". Preview does not run
with the default, so the drainer is not instantiated there and that concern does not apply to
preview. Corrected in the same change as this note; the reasoning behind the drainer is unaffected
and stands for local, CI and any environment without a broker.
