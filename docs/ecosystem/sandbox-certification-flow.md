# Sandbox & Certification Flow

> Status: Implemented | Wave 23 | Date: 2026-03-15

## Overview

Partners integrating with Impilo vNext must pass through a structured certification flow before receiving production credentials. The sandbox provides a safe, rate-limited environment where partners develop and test their integration against real API endpoints with mock data.

## Certification Stages

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ 1. REGISTER │ →  │ 2. SANDBOX  │ →  │ 3. CERTIFY  │ →  │ 4. PROMOTE  │
│             │    │             │    │             │    │             │
│ Create      │    │ Develop &   │    │ Run         │    │ Issue prod  │
│ client      │    │ test in     │    │ contract    │    │ credentials │
│ account     │    │ sandbox     │    │ validation  │    │             │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

## Stage 1: Register

### Prerequisites

- Partner organization approved by Ministry of Health
- Signed data sharing agreement on file
- Technical contact designated

### Steps

```bash
# 1. Register partner client
./scripts/ecosystem/register-partner.sh \
  --name "MedTech EHR" \
  --email "dev@medtech.co.zw" \
  --sandbox

# Output:
#   client_id: <uuid>
#   status: ACTIVE
#   sandbox_enabled: true
```

### What Happens

1. Client record created in `dvp_clients` table
2. Sandbox mode enabled by default
3. Outbox event emitted: `impilo.developer-portal.client.registered.v1`
4. Partner receives client ID

## Stage 2: Sandbox

### Sandbox Environment

| Component | Sandbox Behavior |
|-----------|-----------------|
| API endpoints | Same paths as production (`/internal/v1/...`) |
| Authentication | API key with `sandbox=true` flag |
| Data | Mock patients (CPID-SANDBOX-*), mock facilities |
| Rate limits | 100 requests/minute (vs 1000 in production) |
| FHIR resources | Stored in sandbox-partitioned namespace |
| Events | Published to sandbox Kafka topics (`*.sandbox.*`) |
| Persistence | Isolated database schema (`sandbox_*` tables) |

### Issuing Sandbox Keys

```bash
# 2. Issue sandbox API key
./scripts/ecosystem/issue-partner-keys.sh \
  --client-id <uuid> \
  --label "Sandbox Key" \
  --expires-in-days 30 \
  --sandbox

# Output:
#   key_id: <uuid>
#   api_key: imp_<32chars>  ← Save this! Only shown once.
#   key_prefix: imp_XXXX
#   environment: sandbox
```

### Sandbox Constraints

| Constraint | Value | Enforcement |
|-----------|-------|-------------|
| API key prefix | `imp_` | Generated by developer-portal-service |
| Max key age | 30 days | `expires_at` on `dvp_api_keys` |
| Rate limit | 100 req/min | Envoy rate limit filter |
| Data isolation | Sandbox namespace | Tenant isolation + sandbox flag |
| FHIR write scope | Observation, Encounter only | Policy engine |
| Patient scope | `CPID-SANDBOX-*` only | Prefix check |

### Sandbox Local Profile

For local development, partners can run against a sandbox profile:

```bash
# Start Impilo in sandbox mode (Docker Compose)
docker compose --profile sandbox up -d

# Services available:
#   Developer Portal:  http://localhost:8087
#   Schema Registry:   http://localhost:8088
#   BUTANO (FHIR):     http://localhost:8090
#   TSHEPO (AuthZ):    http://localhost:8081
```

The sandbox profile:
- Starts all services with `SPRING_PROFILES_ACTIVE=sandbox`
- Seeds mock patients and facilities
- Configures reduced rate limits
- Enables sandbox-specific Kafka topics

## Stage 3: Certify

### Contract Certification

Partners must pass automated contract validation before receiving production credentials.

```bash
# 3. Run contract certification
./scripts/ecosystem/run-contract-certification.sh \
  --client-id <uuid> \
  --partner-schema partner-schemas/encounter.json \
  --partner-events partner-events/sample.json

# Output:
#   Contract Certification Report
#   ═══════════════════════════════
#   1. Request Headers:     PASS
#   2. Error Envelope:      PASS
#   3. Event Envelope:      PASS
#   4. Schema Compat:       PASS
#   5. API Versioning:      PASS
#   6. Naming Convention:   PASS
#   ───────────────────────────────
#   Result: CERTIFIED
```

### Certification Checks

| Check | What It Validates | Tool |
|-------|-------------------|------|
| Request Headers | All 4 trust headers present on every request | `GoldenContractSuite` |
| Error Envelope | Partner handles error responses correctly | `EventEnvelopeValidator` |
| Event Envelope | Partner events have all 15 required fields | `EventEnvelopeValidator` |
| Schema Compatibility | Partner schema changes are backward-compatible | `SchemaCompatibilityValidator` |
| API Versioning | Partner uses `/internal/v{N}/` path convention | Path regex check |
| Naming Convention | Event types follow `impilo.{service}.{entity}.{action}.v{N}` | `EventEnvelopeValidator` |
| Idempotency | Partner sends Idempotency-Key on command endpoints | `GoldenContractSuite` |

### Certification Artifacts

After certification, the following artifacts are generated:

```
certification-reports/
  └── {client-id}/
      ├── certification-result.json    # Machine-readable result
      ├── contract-test-report.txt     # Detailed test output
      └── certified-at.txt            # Timestamp
```

### Certification Result Format

```json
{
  "client_id": "<uuid>",
  "client_name": "MedTech EHR",
  "certified": true,
  "certified_at": "2026-03-15T10:30:00Z",
  "checks": {
    "request_headers": "PASS",
    "error_envelope": "PASS",
    "event_envelope": "PASS",
    "schema_compatibility": "PASS",
    "api_versioning": "PASS",
    "naming_convention": "PASS",
    "idempotency": "PASS"
  },
  "schemas_validated": [
    "impilo.partner-ehr.encounter.created.v1"
  ],
  "valid_until": "2027-03-15T10:30:00Z"
}
```

## Stage 4: Promote to Production

### Prerequisites

- All certification checks passed
- Sandbox testing completed (minimum 7 days)
- Partner signed production terms

### Steps

```bash
# 4a. Issue production API key
./scripts/ecosystem/issue-partner-keys.sh \
  --client-id <uuid> \
  --label "Production Key" \
  --expires-in-days 365

# 4b. Configure deprecation posture
curl -X PUT /internal/v1/developer/clients/{id}/deprecation-posture \
  -d '{"posture": "WARN"}'
```

### Production Differences

| Aspect | Sandbox | Production |
|--------|---------|-----------|
| Rate limit | 100 req/min | 1000 req/min |
| Data | Mock (CPID-SANDBOX-*) | Real (CPID-*) |
| Key expiry | 30 days | 365 days |
| Events | Sandbox topics | Production topics |
| Monitoring | Best-effort | Full audit trail |
| SLA | None | Per agreement |

## Key Rotation

Partners should rotate keys before expiry:

```bash
# Rotate key (issues new, revokes old)
curl -X POST /internal/v1/developer/keys/{key_id}/rotate \
  -H "Content-Type: application/json" \
  -d '{"label": "Rotated Key 2026-Q2", "expiresInDays": 365}'
```

## Revocation

Keys can be revoked immediately if compromised:

```bash
# Revoke compromised key
curl -X DELETE /internal/v1/developer/keys/{key_id}

# Response: {"key_id": "<uuid>", "status": "REVOKED"}
```

## Re-Certification

Partners must re-certify when:

| Trigger | Required Action |
|---------|----------------|
| Schema change | Run `run-contract-certification.sh` with new schema |
| API version bump | Update integration code, re-certify |
| Annual renewal | Re-run full certification suite |
| Security incident | Revoke keys, re-certify from Stage 2 |
