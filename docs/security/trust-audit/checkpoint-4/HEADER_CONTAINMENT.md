# Trust-header containment — Checkpoint 4

**Branch:** `claude/tshepo-trust-completion-Yypyl` · **Captured:** 2026-08-02

## The pairing rule

Stripping a client-supplied trust header and regenerating it from validated evidence are **one
control**, not two. Breaking the pair in either direction produces a defect that looks like
hardening:

| Break | Result |
|---|---|
| Strip without regenerate | The header is **deleted**. The upstream loses context it needs, and the outage looks like an unrelated bug. |
| Regenerate without strip | With the PDP off nothing overwrites the client's value, so the anti-impersonation control ends at the gate. |

## What was wrong

The catch-all `/` route stripped only assurance and visibility-obligation headers. It did **not**
strip `x-actor-id`, `x-actor-type`, `x-tenant-id`, `x-subject-id`, `x-provider-id` or
`x-assurance-level`. The design assumed `ext_authz` would overwrite them from the PDP response —
but `envoy.extAuthz.enabled` is `false`, so nothing overwrote anything and those values were
client-forgeable end to end.

## What changed, and what deliberately did not

The six identity headers are now stripped on the catch-all route — **gated on
`extAuthz.enabled`**, because every one of them is re-added from validated evidence by
`PolicyEngine.buildHeaderMutations` through `allowed_upstream_headers`. Stripping them with the
PDP off would not harden anything; it would delete the identity the upstream needs.

**Context headers are deliberately not stripped.** Measured, not assumed: the browser shell
(`ui/one-ui-shell/src/lib/api-client.ts`) genuinely sends all of these, and the PDP regenerates
none of them.

| Header | Sent by shell | Regenerated by PDP | Action |
|---|---|---|---|
| `x-facility-id` | yes | **no** | retained gap |
| `x-workspace-id` | yes | **no** | retained gap |
| `x-department-id` | yes | **no** | retained gap |
| `x-ward-id` | yes | **no** | retained gap |
| `x-programme-id` | yes | **no** | retained gap |
| `x-shift-id` | yes | **no** | retained gap |
| `x-work-context-token` | yes | **no** | retained gap |
| `x-purpose-of-use` | yes | **no** | retained gap |
| `x-workflow-state` | — | **no** | retained gap |

Stripping these would have removed real operating context across the estate — facility scope,
work-context binding and purpose of use all travel in this set. **This is an open gap, not a
solved problem**: those nine headers remain client-supplied. It closes by teaching the PDP to
emit them (so strip and regenerate arrive together), never by stripping them blind.

Consequence to carry into Checkpoint 8: PCT's `ClinicalAccessGuard` waives the care-relationship
check on `purposeOfUse=BREAK_GLASS`, and `x-purpose-of-use` is in the client-supplied set above.
That waiver is client-assertable until this gap closes.

## Gate

`scripts/guard/check-trust-header-strip-pairing.sh` renders the chart with `extAuthz` both off
and on and asserts, for each: no identity header is stripped without a regenerator; no identity
header is stripped while the PDP is disabled; and when the PDP is enabled every header it
regenerates is also stripped.

Proven by breaking it in both directions and confirming RED:
- strip `x-facility-id` with no regenerator → fails
- regenerate `x-provider-id` without stripping it → *"a client value survives when the PDP omits one"*

The gate also refuses to pass if the render yields no `envoy-config` ConfigMap or no catch-all
route — it fired on its own first run, which is how the stdin-consumption bug in it was found.

## Gap closed: the PDP now regenerates operating context

The nine client-supplied headers above are no longer only documented. `ContextHeaderAuthority`
regenerates six of them from the **introspected work-context token** — server-validated in a way a
request header never is — and `x-purpose-of-use` from the closed `PurposeOfUse` vocabulary.

Staged `PASSTHROUGH → SHADOW → AUTHORITATIVE` (default `PASSTHROUGH`).

### Measured live in SHADOW (2026-08-02)

```
tshepo_authz_context_header_total{header="x-facility-id",  outcome="client_only"}   3
tshepo_authz_context_header_total{header="x-workspace-id", outcome="client_only"}   3
tshepo_authz_context_header_total{header="x-purpose-of-use", outcome="match"}       3
```

`client_only` is the finding: the caller asserted a facility and a workspace that the trust plane
**cannot validate**, because no usable work-context token was presented. Those are precisely the
claims `AUTHORITATIVE` drops. The rate is the evidence for whether enabling it is safe — turning it
on blind would remove facility scope from every request whose duty token does not carry one.

The first SHADOW run recorded **zero** metrics: the measurement was called from
`buildHeaderMutations`, which only runs on an ALLOW, so denied traffic measured nothing. That is
the same ALLOW-only blindness fixed earlier in this checkpoint for the OPA comparison, reintroduced
in new code. Emission belongs where headers exist; measurement belongs on the terminal path.

### Still not regenerated — named, not silently omitted

| Header | Why |
|---|---|
| `x-shift-id` | no shift claim exists on the work-context token |
| `x-workflow-state` | no server-validated workflow source exists |
| `x-work-context-token` | a credential, self-authenticating via introspection |

A test asserts the regenerated and unregenerated sets stay disjoint, so neither list can drift into
claiming the other's members.
